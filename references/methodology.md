# 数据库设计方法论（可插拔）

> 本文件是 database-generator-skill 的方法论核心。替换本文件即可切换整套设计风格。
> 当前版本基于 Cursor 社区最佳实践（staged loop + 查询驱动索引）整理。

## 核心原则

1. **约束进数据库，不留在应用层**——只存在于应用代码里的数据规则，早晚会被下一个脚本或运维手工修数据打破。NOT NULL、UNIQUE、CHECK、外键（含明确的 ON DELETE）必须落在 DDL 里。
2. **索引由查询推导，不由清单推导**——每条高频查询都应能点名"是哪个索引在服务我"；没有查询支撑的索引就是负债。
3. **每个阶段留下可检查的产物**——正确性靠测试和 EXPLAIN，不靠人眼读生成的 SQL。
4. **范式化是默认，反范式化是例外**——3NF 起步；反范式必须点名服务的具体查询，写进注释。

## 建模前必须拿到的信息（缺一项就问，不许猜）

- 目标引擎与版本（默认 PostgreSQL 18）
- 实体与关系的自然语言描述（数据文件本身可部分替代）
- 5-10 条最重要/最频繁的查询（含过滤条件和排序）
- 数据量与增长（每年行数）、读写比
- 多租户？数据保留策略？PII / 删除请求 / 审计需求？
- 用户在用的迁移工具（Prisma / Drizzle / Alembic / 裸 SQL）

## 类型选择规则（PostgreSQL 默认）

| 场景 | 选择 |
|---|---|
| 主键 | `bigint generated always as identity` 或 `uuid DEFAULT uuidv7()`（分布式写入才用 uuid） |
| 字符串 | `text`（不用 varchar(n)，除非有真实业务上限） |
| 时间戳 | 一律 `timestamptz` |
| 金额 | `numeric`（不用 float） |
| 布尔 | `boolean`，禁止用 int 0/1 代替 |
| 枚举值 | `text + CHECK (col IN (...))` 起步；枚举值稳定后再考虑 enum 类型 |

其他引擎参考 `references/other-engines.md`。

## 问询点模式（分叉点才问，其他直接做）

原则：能从数据确定性推出的不问（问了显得笨）；语义歧义必须问（猜错返工成本最高）；业务需求必须问（数据里看不出来）。问的时候带证据问选项题，不给开放题。

```
文件 → 类型识别 → 全量扫描画像      （无争议，不问）
    → 【问询点 1】歧义确认           带证据："user_id 有 3 个值在
         │                          users 里不存在，是脏数据还是
         ▼                          允许悬空引用？"
    外键/实体推断 → 三档裁决（adopt 直接用 / ask_user 列出 / ignore）
    → 【问询点 2】需求确认           高频查询、保留策略、PII
         ▼
    建模 → DDL → 验证               （无争议，不问）
```

- **问询点 1（画像后）**：混合类型列、超长文本截断、编码异常、悬空外键值、重复实体跨文件——每项带样本值和统计证据，给 2-3 个选项。
- **问询点 2（建模前）**：方法论"建模前必须拿到的信息"清单中数据本身回答不了的部分。
- 两个问询点可以合并在一次交互里，但不能部跳过；用户不回答时按方法论默认值执行并在报告中标注"默认采用，未经确认"。

## 文件 → 表的映射规则

1. 一个数据文件默认映射为一张表，表名 = 文件名（复数、snake_case）
2. 宽表拆分触发条件（满足其一才拆，拆分需在 ERD 注明）：
   - 存在 1:N 内嵌结构（如一列里是 JSON 数组）→ 拆子表
   - 存在与主键无关的传递依赖 → 违反 3NF 的列组拆出
   - 同一实体信息在多个文件重复出现 → 合并为一张表
3. N:M 关系必须显式中间表，禁止用逗号分隔列
4. 源文件中的"显示顺序""行号"类列若与业务无关 → 丢弃（在交付报告注明）

## 外键判定（由 detect_relations.py 输出，按此裁决）

- 高置信（≥0.8）：名称匹配（`user_id` ↔ `users.id`）且值集 100% 包含 → 直接采用
- 中置信（0.5-0.8）：值集包含但名称不匹配 → 列出证据问用户
- 低置信（<0.5）：仅名称相似 → 忽略，报告里提一句
- 一对一：外键列同时 UNIQUE → 标注 1:1

## 索引推导流程

对每条高频查询：
1. 找到过滤列、排序列、JOIN 列
2. 为其命名一个索引（复合索引列序 = 等值列在前、范围列在后）
3. 每个外键列（JOIN/级联用到时）都要索引——Postgres 不会自动建
4. UNIQUE / 主键已提供的覆盖不重复建

## 约束测试（有数据库时必须全跑）

每条业务规则写一个反向测试：插入一条应被拒绝的行，断言数据库报错。
没被测试过的约束 = 没人知道能不能用的约束。

## 迁移策略

expand-and-contract：加新列/新表（expand）→ 双写迁移数据（migrate）→ 删旧列（contract）。
每次迁移必须带回滚脚本。

## 最终 Checklist（交付前逐项打勾）

- [ ] 每张表都有主键，每列都有明确类型
- [ ] 业务规则全部落在约束里，且每条约束都有反向测试
- [ ] 每条高频查询都有对应索引，EXPLAIN 确认命中
- [ ] 每个外键都有明确的 ON DELETE 策略且能说出理由
- [ ] ERD 与 DDL 一致（表、列、关系三方对齐）
- [ ] seed 脚本可在空库上一次跑通
- [ ] 时间戳全部 timestamptz，金额全部 numeric
- [ ] 反范式化的地方都有注释点名服务的查询
